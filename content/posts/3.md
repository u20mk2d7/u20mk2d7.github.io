Replaced With: Mechanical Sympathy

Mechanical Sympathy focuses on designing software with an understanding of how modern hardware actually executes code.

Key ideas include:

Contiguous memory
Data locality
Compile-time polymorphism
Zero-cost abstractions
Predictable execution
Cache-friendly data structures
Contiguous Memory
       │
       ▼
Data Locality
       │
       ▼
L1/L2 Cache Hit
       │
       ▼
Flat Code / CRTP
       │
       ▼
Predictable Pipeline
       │
       ▼
Sub-Microsecond Latency


Core idea: Instead of optimizing abstractions after the fact, design abstractions that work with the CPU's memory hierarchy and execution model from the beginning.

Key Concepts and Influences

This lecture connects several important software-design concepts:

Uncle Bob's Clean Code principles
SOLID design principles
Gang of Four (GoF) Design Patterns
Design Patterns: Elements of Reusable Object-Oriented Software

These approaches traditionally emphasize maintainability, flexibility, extensibility, and separation of responsibilities.

In performance-critical systems, however, these abstractions need to be evaluated against their runtime costs.

Gang of Four Design Patterns

The GoF design patterns are commonly divided into three categories:

1. Creational Patterns

These patterns provide various object-creation mechanisms, increasing flexibility and reuse of existing code.

Factory Method

Defines an interface for creating an object while allowing subclasses to decide which concrete class to instantiate.

Abstract Factory

Provides an interface for creating families of related or dependent objects without specifying their concrete classes.

Builder

Separates the construction of a complex object from its representation.

Prototype

Creates new objects by copying an existing object.

Singleton

Ensures that a class has only one instance and provides a global access point to it.

2. Structural Patterns

These patterns explain how to assemble objects and classes into larger structures while keeping those structures flexible and efficient.

Adapter

Allows incompatible interfaces to work together.

Bridge

Separates an abstraction from its implementation so that the two can vary independently.

Composite

Composes objects into tree structures to represent part-whole hierarchies.

Decorator

Dynamically adds responsibilities to an object without modifying its underlying class.

Facade

Provides a simplified interface to a larger or more complex subsystem.

Flyweight

Reduces memory usage by sharing common object state between multiple objects.

Proxy

Provides a surrogate or placeholder for another object to control access to it.

3. Behavioral Patterns

These patterns are concerned with algorithms and the assignment of responsibilities between objects.

Chain of Responsibility

Passes a request along a chain of handlers until one of them handles it.

Command

Encapsulates a request as an object, allowing it to be parameterized, queued, logged, or undone.

Iterator

Provides a way to sequentially access elements of a collection without exposing its underlying representation.

Mediator

Defines an object that encapsulates how a set of objects interact with each other.

Memento

Captures and externalizes an object's internal state so it can be restored later.

Observer

Defines a one-to-many dependency so that when one object changes state, its dependents are notified.

State

Allows an object to alter its behavior when its internal state changes.

Strategy

Defines a family of algorithms, encapsulates each one, and makes them interchangeable.

Template Method

Defines the skeleton of an algorithm while allowing subclasses to redefine certain steps.

Visitor

Separates an algorithm from the object structure on which it operates.

Architecture Perspective

The important architectural question is not simply:

"Is this design pattern clean?"

Instead, for performance-critical software, ask:

"What does this abstraction cost at runtime?"

A useful mental model is:

Abstraction
    │
    ├── Maintainability
    ├── Extensibility
    ├── Testability
    │
    └── Runtime Cost
          │
          ├── Memory Access
          ├── Cache Behavior
          ├── Branch Prediction
          ├── Indirection
          └── Instruction Pipeline


The goal of Mechanical Sympathy + Data-Oriented Design is not necessarily to eliminate abstraction, but to make abstraction compatible with the hardware.

Design for humans at compile time. Design for the CPU at runtime.

# 1. Beginner: Optimize for Simplicity and Maintainability

At the beginning, system design is mostly about:

> How can I make this system easy to understand, change, test, and maintain?

**Optimizes for:** separation of responsibilities.

2. Modular Monolith
Optimizes for: simplicity while maintaining strong boundaries.
                Application
                     |
       +-------------+-------------+
       ↓             ↓             ↓
    Users          Orders        Payments

Starting a new product

21. Lock-Free / Wait-Free Design
Optimizes for: reducing blocking and lock contention.
Thread A → Atomic Operation
Thread B → Atomic Operation
Use when:

Optimizes for:

24. Cache-Aware Design
Optimizes for: CPU cache utilization.

The memory hierarchy is approximately:

CPU
 ↓
L1 Cache
 ↓
L2 Cache
 ↓
L3 Cache
 ↓
RAM

The closer data is to the CPU, the lower the access latency generally is.

Use when:

CPU performance is the bottleneck
You process large datasets
Memory access patterns dominate performance

25. NUMA-Aware Design
Optimizes for: memory locality in multi-socket systems.

CPU 0 ─── Memory 0
  |
  | slower remote access
  ↓
Memory 1 ─── CPU 1

Use when:

Running on large multi-socket servers
Memory bandwidth matters
CPU-to-memory locality affects performance

26. SIMD / Vectorization
Optimizes for: doing many operations per CPU instruction.

Scalar:

A1 + B1
A2 + B2
A3 + B3
A4 + B4

SIMD:

[A1 A2 A3 A4]
       +
[B1 B2 B3 B4]

Use when:

Performing the same operation over large arrays
Image/audio processing
Numerical computing

27. Zero-Copy Design
Optimizes for: reducing unnecessary memory copies.

Traditional:

Disk
 ↓

28. Real-Time System Design
Optimizes for: predictable timing.

The important question is not necessarily:

Is it fast?

It is:

Can I guarantee that this operation completes within a deadline?

Good:

# The Big Picture
Do not think of these as 30 competing architectures.

They are different optimization dimensions.

                     SYSTEM DESIGN
                          |
          +---------------+---------------+
          |               |               |
          ↓               ↓               ↓
    Maintainability   Scalability     Performance
          |               |               |
        OOD              DDD              DOD
        SOLID        Microservices        SIMD
        Clean        Event-driven         NUMA
        Hexagonal    Distributed          Zero-copy
          |               |               |
          +---------------+---------------+
                          |
                  Mechanical Sympathy
                          |
                  Hardware-aware design

A real system can combine many of these approaches.
                    E-Commerce System
                           |
              +------------+------------+
              |                         |
             DDD                   Microservices
              |                         |
       Bounded Contexts           Event-Driven
              |                         |
              +------------+------------+
                           |
                       CQRS / Saga
                           |
                           ↓
                  High-performance service
                           |
                           ↓
                    DOD / SIMD / Cache
                           |
                           ↓
                  Mechanical Sympathy
The key mental model is:

System design is not one hierarchy where you choose one philosophy.

Instead, you choose techniques from different layers depending on the problem, bottleneck, scale, and performance requirements.

A Practical Learning Path
If you want to learn these concepts in a sensible order:
Level 1 -> Clean Code -> SOLID -> OOD -> Layered Architecture -> Modular Monolith
Level 2 -> DDD -> Clean Architecture -> Hexagonal Architecture -> Event-Driven Architecture -> Message Queues
Level 3 -> Microservices -> CQRS -> Event Sourcing -> Saga -> Distributed Systems
Level 4 -> Concurrency -> Actor Model -> Lock-Free Programming -> Memory Model -> CPU Cache
Level 5 -> Data-Oriented Design -> Mechanical Sympathy -> Cache-Aware Programming -> SIMD -> NUMA -> Zero-Copy
Level 6 -> Real-Time Systems -> HPC -> Ultra-Low-Latency Systems -> Hardware-Aware Architecture

The most important progression is:

Code Design → Application Architecture → Distributed Systems → Concurrency → Hardware → Extreme Performance
