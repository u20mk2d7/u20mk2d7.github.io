The Progressive Path to High-Frequency Trading (HFT) in C++

Welcome to HFT development! Building a high-frequency trading system is one of the most challenging and rewarding engineering feats. Do not start by trying to build a real production HFT system. Instead, build progressively smaller systems where each project teaches one core performance concept.

This guide outlines the first two foundational steps of that journey: mastering modern low-latency C++ and building a simple Order Book, followed by understanding exchange mechanics and implementing a Matching Engine.

Phase 1: C++ Fundamentals for Low-Latency Programming
Before worrying about microseconds or network cards, you must master the subset of C++ used in low-latency environments. In HFT, safety, determinism, and zero overhead are paramount (avoiding garbage collection, dynamic memory allocation in the hot path, and cache misses).

Key Concepts to Master
References, pointers, & RAII (Resource Acquisition Is Initialization): Understand object lifecycles deterministically without relying on runtime garbage collection.

Move semantics: Eliminate unnecessary deep copies of data structures to keep latency down.

Templates (Metaprogramming): Leverage compile-time polymorphism to avoid virtual function table (vtable) lookup overhead.

Standard Containers (std::vector, std::array, std::deque): Understand their underlying memory layouts. std::vector and std::array guarantee contiguous memory, which is essential for CPU cache locality.

Smart pointers (std::unique_ptr, std::shared_ptr): Know when to use unique ownership (prefer unique_ptr or raw pointers) and why shared ownership introduces atomic reference counting overhead.

std::atomic: Learn lock-free programming primitives for thread-safe communication.

Threads and synchronization: Understand mutexes, condition variables, and spinning vs. blocking.

Memory layout and alignment: Learn about cache lines (typically 64 bytes), padding, and how false sharing impacts multi-threaded performance.

constexpr: Shift computations from runtime to compile-time.

C++20/23 features: Leverage concepts, coroutines, and ranges where applicable without introducing runtime overhead.

Linux system programming: Familiarize yourself with POSIX threads, CPU pinning (pthread_setaffinity_np), and high-resolution timers.

Coding Project 1: Build a Simple Order Book
An order book maintains the collection of limit orders for a financial instrument, organized by price levels.

Order Book Layout Example:
Order Book
---------------------------------
ASK         101.5     200
            101.4     100
            101.3     500
---------------------------------
BID         101.2     300
            101.1     150
            101.0     400
---------------------------------


Core Interface to Implement
Your order book class should support the following primary operations:

add_order(): Insert a new limit order into the book.

cancel_order(): Remove an existing order by its unique ID.

modify_order(): Change the price or size of an existing order.

execute_order(): Process a trade/fill against an order.

best_bid(): Retrieve the highest price buyers are willing to pay.

best_ask(): Retrieve the lowest price sellers are willing to accept.

Performance Tip for Beginners
While a production HFT order book often uses intrusive data structures or pre-allocated memory pools (object pools) to avoid heap allocation (new/delete) during trading hours, start by building a functional version using hash maps for fast O(1) order lookup and sorted containers or vectors for price levels.

Core Concepts to Learn
Limit Order: An order to buy or sell at a specific price or better.

Market Order: An order to buy or sell immediately at the best available current price.

Bid / Ask: The highest price a buyer is willing to pay (Bid) vs. the lowest price a seller is willing to accept (Ask).

Spread: The difference between the lowest ask price and the highest bid price.

Tick Size: The minimum legal price increment by which a security can move.

Matching Engine: The core exchange software component that matches buy and sell orders.

FIFO / Price-Time Priority: The primary matching rule where orders at the better price are matched first, and at the same price, orders are matched in the order they arrived.

Market Data, Trades, & Acknowledgements: How exchanges broadcast feeds (trades, book updates) and confirm order actions back to participants.

Partial Fills: Situations where an incoming order is too large for a single resting order, resulting in multiple partial executions.

Coding Project 2: Build Your Own Matching Engine
Building your own matching engine is one of the best beginner HFT projects because it teaches you what the rest of the trading ecosystem is actually doing under the hood.

Example Scenario
Suppose your engine processes the following sequence:
BUY   100 @ 101
BUY   200 @ 100
SELL  150 @ 101

Engine Behavior Expectations
The first order (BUY 100 @ 101) rests in the book as the best bid.

The second order (BUY 200 @ 100) rests behind it at a lower price level.

The incoming SELL 150 @ 101 matches against the resting BUY 100 @ 101 first (Price-Time Priority).

The incoming sell order is partially filled (100 units matched at 101), leaving 50 units remaining. Depending on your engine design, those remaining 50 units can either rest on the ask side or be canceled (Immediate-or-Cancel).

Implementation Goals
Implement order queues for each price level.

Enforce FIFO matching rules.

Generate trade execution reports (e.g., printing out trade price and matched quantities).


Once you successfully complete the Order Book and Matching Engine projects, you will understand memory layout, basic state management, and event processing. From there, you can progress to:

Concurrency & Lock-Free Data Structures: Single-producer single-consumer (SPSC) ring buffers.

Network Programming: Using raw sockets, TCP/IP tuning, and parsing binary market data feeds (e.g., ITCH/OUCH protocols).

Hardware Optimization: CPU cache optimization, minimizing branch mispredictions, and kernel bypass (Solarflare EF_VI / DPDK).

Lesson 2 — What is a price level?
Suppose we receive:

BUY 1001 100.00 100
BUY 1002 100.00 200
BUY 1003 100.01 150

The book becomes:

BUY

100.00 → 300

There are three orders but only two price levels.

So conceptually we have:

Price Level
    │
    ├── Order
    ├── Order
    └── Order

For example:

100.00
  │

Order Book
   │

   │      ├── Orders
   │      ├── Orders
   │      └── Orders
   │

Lesson 3 — Price-time priority
For a simple exchange matching engine, we'll use:

Price priority first, then time priority.

Suppose:

BUY 1001 @ 100.00 qty 100
BUY 1002 @ 101.00 qty 100
BUY 1003 @ 101.00 qty 200

The book is:

101.00
 ├── 1002   ← first
 └── 1003   ← second

100.00
 └── 1001

If someone sells:

SELL @ 101.00 qty 150

then:

1002 gets 100
1003 gets 50

because order 1002 arrived first.

That's FIFO at the same price.

Our first implementation can use the STL.

order_book.hpp
#pragma once

#include <cstdint>
#include <map>
#include <unordered_map>
#include <vector>

enum class Side {
    Buy,
    Sell
};

using OrderId = std::uint64_t;
using Price = std::int64_t;
using Quantity = std::uint64_t;

struct Order {
    OrderId id;
    Side side;
    Price price;
    Quantity quantity;
};

class OrderBook {
public:
    bool add_order(
        OrderId id,
        Side side,
        Price price,
        Quantity quantity
    );

    bool cancel_order(OrderId id);

    Quantity best_bid() const;
    Quantity best_ask() const;

private:
    using Orders = std::vector<Order>;

    std::map<Price, Orders, std::greater<>> bids_;
    std::map<Price, Orders> asks_;

    std::unordered_map<OrderId, Order*> orders_;
};

There is an issue with this implementation that we'll deliberately discover later: pointers into std::vector can become invalid when the vector reallocates.

That's useful for learning.

We shouldn't blindly jump to a "perfect HFT implementation."

Lesson 5 — First implementation
Let's make add_order() work.

#include "order_book.hpp"

bool OrderBook::add_order(
    OrderId id,
    Side side,
    Price price,
    Quantity quantity
) {
    if (quantity == 0) {
        return false;
    }

    if (orders_.contains(id)) {
        return false;
    }

    Order order{
        .id = id,
        .side = side,
        .price = price,
        .quantity = quantity
    };

    if (side == Side::Buy) {
        auto& level = bids_[price];
        level.push_back(order);

        orders_[id] = &level.back();
    } else {
        auto& level = asks_[price];
        level.push_back(order);

        orders_[id] = &level.back();
    }

    return true;
}

Lesson 6 — Best bid / ask
For bids, the highest price is best.

Because we declared:

std::map<Price, Orders, std::greater<>>

the first element is the highest price.

Quantity OrderBook::best_bid() const
{
    if (bids_.empty()) {
        return 0;
    }

    return bids_.begin()->first;
}

But notice something:

The function is called:

best_bid()

Yet we're returning a Quantity.

That's wrong.

We should return Price.

So change:

Price best_bid() const;
Price best_ask() const;

and:

Price OrderBook::best_bid() const
{
    if (bids_.empty()) {
        return 0;
    }

    return bids_.begin()->first;
}

Price OrderBook::best_ask() const
{
    if (asks_.empty()) {
        return 0;
    }

    return asks_.begin()->first;
}

This kind of mistake is exactly why we're going to build tests early.

One important correction before we continue
The code above intentionally exposes a problem:

orders_[id] = &level.back();

because level is a std::vector<Order>.

When the vector grows, it can reallocate and invalidate those pointers.

Don't "fix" this yet. This is going to become our first performance/data-structure lesson.

We'll first get the basic version working, write tests around it, then benchmark it, find the problem, and replace the data structure based on evidence.
