# C++ Coding Guidelines for AI Agents

## 1. Purpose

This document defines the coding standards an AI coding agent MUST follow when writing, modifying, reviewing, or refactoring C++ code in this project.

Core Foundations & Standards
- Primary Target: C++23 or newer.
- Style & Design: Follows Uncle Bob's Clean Code, SOLID principles, Google C++ Style Guide formatting/naming, and C++ Core Guidelines for safety and modern design.
- Rule Priority: Project-specific rules > Correctness/Safety > C++23+ best practices > C++ Core Guidelines > Google C++ Style Guide > Existing project conventions. 
The goal is code that is:

* Correct
* Safe
* Modern
* Readable
* Maintainable
* Efficient without premature optimization
* Consistent with the existing project architecture

---

# 2. Rule Priority

When rules conflict, apply them in this order:

1. **Project-specific rules**
2. **Correctness and safety**
3. **C++23+ language/library best practices**
4. **C++ Core Guidelines**
5. **Google C++ Style Guide**
6. Existing project conventions

Do not blindly change existing code merely to make it conform to these guidelines. Preserve established project conventions unless the task requires a change or the existing code introduces a real problem.

---

# 3. C++ Version

## 3.1 Use C++23+

The project targets **C++23 or newer**.

Prefer standard C++23 facilities over:

* C-style constructs
* custom implementations of standard functionality
* obsolete C++ patterns
* compiler-specific extensions when a standard solution exists

Use newer language features when they improve correctness, readability, or maintainability.

Examples include:

```cpp
std::expected
std::optional
std::span
std::string_view
std::ranges
std::format
std::print
std::source_location
std::mdspan
std::jthread
std::stop_token
constexpr
consteval
constinit
concepts
```

Do not use a modern feature merely because it exists. Prefer the simplest solution that clearly expresses the intent.

---

# 4. General Principles

Follow these principles:

* Prefer simple code over clever code.
* Make invalid states difficult to represent.
* Prefer compile-time checking over runtime checking when practical.
* Prefer value semantics.
* Minimize mutable global state.
* Minimize shared ownership.
* Make ownership explicit.
* Use RAII for resource management.
* Keep interfaces small and focused.
* Prefer standard library facilities.
* Avoid unnecessary abstraction.
* Avoid premature optimization.
* Optimize only when there is evidence that optimization matters.
* Keep functions short and focused.
* Prefer composition over inheritance when appropriate.
* Use strong types instead of primitive-type ambiguity.
* Make APIs difficult to misuse.

---

# 5. Formatting

Follow the **Google C++ Style Guide** formatting conventions.

Use:

* Consistent indentation
* Consistent brace placement
* Reasonable line length
* Spaces around operators
* Clear whitespace
* Consistent formatting throughout the file

Use automated formatting when the project provides a formatter configuration.

Preferred formatter:

```text
clang-format
```

If the repository contains:

```text
.clang-format
```

that configuration takes precedence over generic formatting rules.

Do not manually reformat unrelated code.

---

# 6. Naming

Follow Google-style naming conventions unless the existing project has a stronger established convention.

## 6.1 Types

Use `PascalCase`:

```cpp
class NetworkConnection;
struct UserProfile;
enum class ConnectionState;
```

## 6.2 Functions

Use `PascalCase` for functions:

```cpp
void InitializeConnection();
bool IsConnected();
std::string GetName();
```

Follow the project's existing convention if it intentionally differs.

## 6.3 Variables

Use `snake_case`:

```cpp
int connection_count;
std::string user_name;
bool is_initialized;
```

## 6.4 Constants

Use project-consistent naming.

Prefer meaningful names:

```cpp
constexpr int kMaxConnections = 64;
constexpr std::size_t kDefaultBufferSize = 4096;
```

## 6.5 Namespaces

Use lowercase:

```cpp
namespace my_project {
namespace networking {
}
}  // namespace my_project::networking
```

Prefer modern nested namespace syntax when appropriate:

```cpp
namespace my_project::networking {
}
```

## 6.6 Avoid Bad Names

Avoid:

```cpp
int x;
int tmp;
int data;
int thing;
int foo;
```

unless the scope and meaning genuinely make the name obvious.

Prefer:

```cpp
int retry_count;
std::size_t bytes_read;
ConnectionState connection_state;
```

# 7. Header Files

Prefer `#pragma once` unless the project explicitly requires traditional include guards.

```cpp
#pragma once
```

Include what you use.

Do not rely on transitive includes.

Bad:

```cpp
#include "foo.h"

// Works only because foo.h happens to include <string>.
std::string name;
```

Good:

```cpp
#include <string>
```

Keep includes organized consistently with the project.

Typical order:

1. Corresponding header
2. C system headers
3. C++ standard library headers
4. Third-party headers
5. Project headers

Example:

```cpp
#include "network/client.h"

#include <cstdint>
#include <string>
#include <vector>

#include "network/connection.h"
```

Use forward declarations when they meaningfully reduce dependencies and are safe to use.

Do not use forward declarations unnecessarily.

---

# 8. Ownership and RAII

Resource ownership must be explicit.

Prefer RAII.

Good:

```cpp
std::ifstream file(path);
```

Good:

```cpp
std::unique_ptr<Widget> widget = std::make_unique<Widget>();
```

Avoid manual ownership:

```cpp
Widget* widget = new Widget();

delete widget;
```

Prefer:

```cpp
auto widget = std::make_unique<Widget>();
```

---

# 9. Smart Pointers

## 9.1 `std::unique_ptr`

Use `std::unique_ptr` to express exclusive ownership.

```cpp
std::unique_ptr<Connection> connection;
```

Prefer:

```cpp
auto connection = std::make_unique<Connection>();
```

over:

```cpp
std::unique_ptr<Connection> connection(new Connection());
```

## 9.2 `std::shared_ptr`

Use `std::shared_ptr` only when shared ownership is genuinely required.

Do not use `shared_ptr` simply because ownership is unclear.

Bad:

```cpp
std::shared_ptr<Widget> widget;
```

when there is only one owner.

Prefer:

```cpp
std::unique_ptr<Widget> widget;
```

## 9.3 Raw Pointers

A raw pointer should generally represent:

* non-owning access
* optional access where `nullptr` has explicit meaning
* interoperability with APIs that require pointers

Do not use raw pointers to represent ownership.

---

# 10. References and Views

Prefer references for required non-owning access:

```cpp
void Process(const User& user);
```

Use pointers when `nullptr` is meaningful:

```cpp
void Process(User* user);
```

For contiguous non-owning data, prefer:

```cpp
std::span<const std::byte>
```

instead of:

```cpp
const std::byte* data,
std::size_t size
```

For read-only strings, consider:

```cpp
std::string_view
```

when lifetime requirements are satisfied.

Do not return `std::string_view` or `std::span` to data whose lifetime ends when the function returns.

---

# 11. Const Correctness

Use `const` aggressively where it communicates intent.

Prefer:

```cpp
void Print(const std::string& name);
```

over:

```cpp
void Print(std::string& name);
```

if the function does not modify the string.

Use:

```cpp
const auto value = Calculate();
```

when immutability improves clarity.

Do not add `const` mechanically when it makes the code harder to read.

---

# 12. `auto`

Use `auto` when it improves readability or avoids redundant type spelling.

Good:

```cpp
auto connection = std::make_unique<Connection>();
```

Good:

```cpp
for (const auto& connection : connections) {
  connection.Send();
}
```

Good:

```cpp
auto iterator = map.find(key);
```

Avoid `auto` when the type is important to understanding the code.

For example:

```cpp
auto timeout = 1000;
```

may hide whether the value is milliseconds, seconds, or another unit.

Prefer a meaningful type:

```cpp
constexpr std::chrono::milliseconds kTimeout{1000};
```

---

# 13. Initialization

Prefer uniform initialization where appropriate:

```cpp
int count{0};
std::string name{"Alice"};
std::vector<int> values{1, 2, 3};
```

Avoid uninitialized variables.

Bad:

```cpp
int count;
```

Good:

```cpp
int count{};
```

Prefer initialization at declaration.

---

# 14. `nullptr`

Never use `NULL` or `0` as a null pointer.

Bad:

```cpp
Widget* widget = NULL;
```

Bad:

```cpp
Widget* widget = 0;
```

Good:

```cpp
Widget* widget = nullptr;
```

---

# 15. Casts

Avoid C-style casts:

```cpp
int value = (int)count;
```

Use an explicit C++ cast when conversion is required:

```cpp
int value = static_cast<int>(count);
```

Use the correct cast:

* `static_cast`
* `const_cast`
* `dynamic_cast`
* `reinterpret_cast`

Avoid `reinterpret_cast` unless there is a strong, documented reason.

Avoid unnecessary casts.

---

# 16. Containers

Prefer standard containers.

Examples:

```cpp
std::vector<T>
std::array<T, N>
std::deque<T>
std::list<T>
std::map<K, V>
std::unordered_map<K, V>
std::set<T>
std::unordered_set<T>
```

Use the container whose semantics match the problem.

Do not default to `std::list`.

In many cases, `std::vector` has better cache behavior and should be preferred unless another container provides a real advantage.

Prefer:

```cpp
std::array<int, 4>
```

over:

```cpp
int values[4];
```

for fixed-size arrays in modern C++.

---

# 17. Algorithms and Ranges

Prefer standard algorithms and ranges over manual loops when they make intent clearer.

Prefer:

```cpp
std::ranges::sort(values);
```

over manually implementing sorting.

Prefer:

```cpp
if (std::ranges::contains(values, value)) {
  ...
}
```

when appropriate.

Avoid writing custom implementations of standard algorithms.

However, do not force ranges into code when a simple loop is significantly clearer.

Readability wins.

---

# 18. Loops

Prefer range-based loops.

Good:

```cpp
for (const auto& item : items) {
  Process(item);
}
```

Instead of:

```cpp
for (std::size_t i = 0; i < items.size(); ++i) {
  Process(items[i]);
}
```

Use indexed loops only when the index is actually required.

---

# 19. Strings

Use:

```cpp
std::string
```

for owned strings.

Use:

```cpp
std::string_view
```

for non-owning read-only string access when lifetime is safe.

Avoid unnecessary string copies.

Do not use C strings unless required for interoperability.

Prefer:

```cpp
std::string name;
```

over:

```cpp
char name[256];
```

for normal application code.

---

# 20. Error Handling

Choose an error-handling mechanism based on the API semantics.

For expected failures, prefer explicit result types such as:

```cpp
std::optional<T>
```

when only success/failure is required.

Use:

```cpp
std::expected<T, E>
```

when the caller needs structured error information.

Example:

```cpp
std::expected<User, Error> LoadUser(UserId id);
```

Use exceptions when they fit the project's error-handling model and are appropriate for exceptional failures.

Do not use exceptions and `std::expected` inconsistently within the same subsystem without a clear architectural reason.

Never silently ignore errors.

Bad:

```cpp
LoadConfiguration();
```

if failure matters.

Better:

```cpp
auto result = LoadConfiguration();
if (!result) {
  LogError(result.error());
  return;
}
```

---

# 21. Optional Values

Use `std::optional<T>` when a value may legitimately be absent.

Good:

```cpp
std::optional<User> FindUser(UserId id);
```

Avoid sentinel values.

Bad:

```cpp
int FindUser();
```

where `-1` means "not found".

Prefer:

```cpp
std::optional<int> FindUser();
```

---

# 22. Enumerations

Prefer scoped enums:

```cpp
enum class ConnectionState {
  kDisconnected,
  kConnecting,
  kConnected,
};
```

Avoid unscoped enums unless there is a specific reason.

Do not rely on implicit integer conversions.

---

# 23. Strong Types

Avoid using primitive types for values with different semantic meanings.

Bad:

```cpp
void Connect(int timeout, int port);
```

Better:

```cpp
void Connect(std::chrono::milliseconds timeout, std::uint16_t port);
```

Use strong types when they prevent invalid or ambiguous usage.

---

# 24. Integer Types

Use the appropriate integer type.

Examples:

```cpp
std::uint32_t
std::int64_t
std::size_t
std::ptrdiff_t
```

Use `std::size_t` for container sizes and indexes when appropriate.

Avoid mixing signed and unsigned integers unnecessarily.

Be careful with implicit conversions and narrowing.

---

# 25. Time

Do not represent durations as unexplained integers.

Bad:

```cpp
Sleep(5000);
```

Better:

```cpp
Sleep(std::chrono::seconds{5});
```

Prefer `<chrono>` types:

```cpp
std::chrono::milliseconds
std::chrono::seconds
std::chrono::steady_clock
std::chrono::system_clock
```

Use `steady_clock` for elapsed-time measurement.

---

# 26. Constructors

Prefer constructors that establish a valid object state.

Avoid partially initialized objects.

Use `explicit` for single-argument constructors unless implicit conversion is intentionally part of the API.

Good:

```cpp
class UserId {
 public:
  explicit UserId(std::uint64_t value);
};
```

Avoid:

```cpp
UserId(std::uint64_t value);
```

unless implicit conversion is desired.

---

# 27. Special Member Functions

Follow the Rule of Zero whenever possible.

Prefer designing classes so that the compiler-generated:

* destructor
* copy constructor
* copy assignment
* move constructor
* move assignment

are correct.

Avoid manually implementing special member functions unless necessary.

Prefer composition with RAII-enabled standard types.

---

# 28. Classes

Keep classes focused.

A class should have a clear responsibility.

Avoid "god classes" that manage unrelated concerns.

Prefer:

```text
Connection
ConnectionManager
ConnectionConfig
ConnectionStatistics
```

over one huge class containing everything.

Keep implementation details private.

Expose the smallest useful public interface.

---

# 29. Inheritance

Use inheritance when there is a genuine "is-a" relationship and polymorphism is required.

Prefer composition when appropriate.

If a class is intended to be used polymorphically, give it a virtual destructor:

```cpp
class Interface {
 public:
  virtual ~Interface() = default;
  virtual void Process() = 0;
};
```

Use `override` whenever overriding a virtual function:

```cpp
void Process() override;
```

Never omit `override` when it is applicable.

Use `final` when preventing further inheritance or overriding is intentional.

---

# 30. Virtual Interfaces

Keep interfaces small.

Prefer:

```cpp
class Logger {
 public:
  virtual ~Logger() = default;
  virtual void Log(std::string_view message) = 0;
};
```

over interfaces with many unrelated operations.

Dependency injection should use the smallest interface necessary.

---

# 31. Templates and Concepts

Prefer concepts over complicated SFINAE when C++23 concepts can express the requirement clearly.

Good:

```cpp
template <typename T>
concept Serializable = requires(const T& value) {
  Serialize(value);
};
```

Then:

```cpp
template <Serializable T>
void Write(const T& value);
```

Prefer clear constraints over complicated template metaprogramming.

Do not use templates merely to demonstrate generic programming.

---

# 32. `constexpr`, `consteval`, and `constinit`

Use compile-time evaluation when it provides a real benefit.

Use:

```cpp
constexpr
```

for values/functions that can and should be evaluated at compile time.

Use:

```cpp
consteval
```

when a function must execute at compile time.

Use:

```cpp
constinit
```

for static/thread storage variables that must have constant initialization.

Do not add these keywords without understanding their semantic purpose.

---

# 33. `constexpr` Constants

Prefer named constants instead of magic numbers.

Bad:

```cpp
if (retry_count > 3) {
```

Better:

```cpp
constexpr int kMaxRetries = 3;

if (retry_count > kMaxRetries) {
```

Prefer domain-specific types when appropriate.

---

# 34. Formatting and Output

Prefer modern C++ formatting facilities.

When supported by the project's standard library:

```cpp
std::format
std::print
std::println
```

Prefer them over complex stream formatting or C-style formatting when they improve clarity.

Avoid unsafe C-style formatting such as:

```cpp
sprintf
vsprintf
```

Use safer standard facilities.

---

# 35. Memory

Avoid manual memory management.

Do not use:

```cpp
malloc
calloc
realloc
free
```

in normal C++ application code.

Prefer:

```cpp
std::vector
std::string
std::array
std::unique_ptr
std::shared_ptr
```

when appropriate.

For low-level systems code, manual allocation may be necessary, but ownership and lifetime must be explicit.

---

# 36. Move Semantics

Use move semantics where they naturally improve ownership transfer.

Do not write:

```cpp
return std::move(local);
```

for an ordinary local return value.

Prefer:

```cpp
return local;
```

and allow return-value optimization / implicit move to work.

Do not use `std::move` on objects that still need to be used afterward.

After moving from an object, assume only its valid-but-unspecified state unless the type documents stronger guarantees.

---

# 37. Perfect Forwarding

Use forwarding references and `std::forward` only when implementing genuinely generic forwarding interfaces.

Do not use:

```cpp
template <typename T>
void Foo(T&& value);
```

automatically for every function.

Prefer simple interfaces when forwarding is unnecessary.

---

# 38. Lambdas

Keep lambdas short and readable.

Prefer explicit captures when they make ownership and dependencies clearer.

Avoid broad captures such as:

```cpp
[&]
```

when explicit captures are more appropriate.

Be especially careful when lambdas outlive the current scope.

Never capture references to objects whose lifetime may end before lambda execution.

---

# 39. Concurrency

Prefer modern standard concurrency facilities.

Use:

```cpp
std::jthread
std::stop_token
std::mutex
std::scoped_lock
std::lock_guard
std::unique_lock
std::condition_variable
std::atomic
```

Prefer RAII-based locking:

```cpp
std::scoped_lock lock(mutex_);
```

Avoid manual:

```cpp
mutex.lock();
...
mutex.unlock();
```

Do not introduce concurrency without a clear need.

Avoid data races.

Document synchronization assumptions when they are not obvious.

---

# 40. Atomics

Use atomics only when their memory semantics are understood.

Do not replace a mutex with an atomic merely for perceived performance.

Choose the weakest memory ordering that is correct, but prioritize correctness and readability.

If memory ordering is nontrivial, document why it is required.

---

# 41. Exceptions

Follow the project's exception policy.

When exceptions are enabled:

* Do not throw from destructors.
* Preserve exception safety.
* Use RAII.
* Avoid catch-and-rethrow without adding useful context.
* Do not catch exceptions merely to suppress them.
* Catch by reference.

Prefer:

```cpp
catch (const std::exception& error) {
  ...
}
```

over:

```cpp
catch (std::exception error) {
  ...
}
```

---

# 42. `noexcept`

Use `noexcept` when an operation is genuinely guaranteed not to throw and the semantic benefit is meaningful.

Especially consider it for:

* destructors
* move constructors
* move assignment operators
* low-level operations where the contract requires it

Do not mark functions `noexcept` merely to silence compiler warnings.

---

# 43. Assertions

Use assertions for programmer assumptions and invariants.

Example:

```cpp
assert(index < values.size());
```

Do not use assertions as a substitute for handling expected runtime failures.

Bad:

```cpp
assert(file.is_open());
```

if a missing file is a legitimate runtime condition.

---

# 44. Logging

Use the project's existing logging framework.

Do not introduce a new logging framework without explicit architectural approval.

Avoid logging:

* secrets
* passwords
* authentication tokens
* private keys
* sensitive user data

Use appropriate log levels.

Avoid excessive logging in hot paths.

---

# 45. Comments

Write comments that explain **why**, not obvious **what**.

Bad:

```cpp
// Increment i.
++i;
```

Good:

```cpp
// Retry once because the service may still be initializing.
++retry_count;
```

Keep comments accurate.

Update comments when changing the code they describe.

Do not add comments that merely restate the implementation.

---

# 46. TODOs

Use TODOs only when there is a real follow-up task.

Good:

```cpp
// TODO(username): Replace polling with event-driven notification.
```

Avoid vague TODOs:

```cpp
// TODO: Fix this.
```

---

# 47. API Design

Design APIs around clear contracts.

Prefer:

```cpp
std::expected<Response, Error> Send(const Request& request);
```

over APIs that require callers to inspect undocumented global state.

Make ownership explicit.

Make lifetime requirements clear.

Prefer types that express units and constraints.

---

# 48. Avoid Magic Values

Bad:

```cpp
if (status == 7) {
```

Better:

```cpp
if (status == Status::kReady) {
```

Bad:

```cpp
buffer.resize(4096);
```

when the number has domain meaning.

Better:

```cpp
constexpr std::size_t kDefaultBufferSize = 4096;
buffer.resize(kDefaultBufferSize);
```

---

# 49. Avoid C-Style APIs

Prefer C++ abstractions when possible.

Avoid:

```cpp
char* buffer;
memcpy(...);
strlen(...);
printf(...);
malloc(...);
free(...);
```

Prefer appropriate C++ facilities:

```cpp
std::string
std::span
std::copy
std::ranges
std::format
std::vector
```

C APIs are acceptable when required for:

* OS APIs
* hardware interfaces
* third-party libraries
* ABI boundaries
* legacy interoperability

Wrap unsafe APIs behind safe abstractions when practical.

---

# 50. File and Resource Handling

Every acquired resource must have a clear owner and lifetime.

Examples:

* files
* sockets
* locks
* threads
* database connections
* OS handles
* GPU resources
* memory

Prefer RAII wrappers.

A function that acquires a resource should not leave ownership ambiguous.

---

# 51. API Lifetime Safety

Be careful with returned references and views.

Never return references, pointers, `std::span`, or `std::string_view` to local objects.

Bad:

```cpp
std::string_view GetName() {
  std::string name = "Alice";
  return name;
}
```

Good:

```cpp
std::string GetName() {
  return "Alice";
}
```

---

# 52. Performance

Performance matters, but correctness and maintainability come first.

Do not optimize based on assumptions.

Prefer:

1. Correctness
2. Clear design
3. Appropriate data structures
4. Measurement
5. Targeted optimization

Avoid unnecessary:

* allocations
* copies
* synchronization
* virtual dispatch
* conversions

But do not sacrifice readability for negligible theoretical performance gains.

---

# 53. `std::move` and Copies

Avoid unnecessary copies when ownership transfer is intended.

Good:

```cpp
class User {
 public:
  explicit User(std::string name)
      : name_(std::move(name)) {}

 private:
  std::string name_;
};
```

For small types, copying may be clearer and cheaper than introducing complicated move logic.

Do not optimize every parameter for move semantics without evidence.

---

# 54. Error-Prone Patterns to Avoid

Avoid:

```cpp
#define
NULL
0                  // as null pointer
malloc/free
new/delete
C-style casts
reinterpret_cast   // unless necessary
goto               // unless justified by low-level/resource logic
using namespace std;
std::shared_ptr    // without shared ownership
raw owning pointers
magic numbers
uninitialized variables
implicit narrowing
unchecked return values
broad lambda captures
manual mutex unlock
unnecessary inheritance
unnecessary templates
premature optimization
```

Some low-level code may legitimately require these constructs. If so, document the reason.

---

# 55. `using namespace`

Do not write:

```cpp
using namespace std;
```

especially in headers.

Prefer:

```cpp
std::string
std::vector
std::optional
```

Namespace aliases may be used when they significantly improve readability:

```cpp
namespace fs = std::filesystem;
```

---

# 56. Header Hygiene

Headers should be self-contained.

Every header should compile when included independently where practical.

Avoid unnecessary dependencies.

Do not put `using namespace` directives in headers.

Avoid defining non-inline global variables in headers.

Prefer:

```cpp
inline constexpr
```

for header-defined constants where appropriate.

---

# 57. Source File Organization

A typical implementation file should follow the project's established structure.

For example:

```cpp
#include "project/widget.h"

#include <algorithm>
#include <string>

#include "project/helper.h"

namespace project {

Widget::Widget(...) {
  ...
}

void Widget::Process() {
  ...
}

}  // namespace project
```

Do not reorganize unrelated files without a reason.

---

# 58. Tests

Every meaningful behavior change should consider whether tests are required.

Prefer tests that verify behavior rather than implementation details.

Tests should be:

* deterministic
* isolated
* readable
* fast where practical

Avoid tests that depend unnecessarily on:

* timing
* global state
* network availability
* filesystem layout
* execution order

Use the project's existing testing framework.

---

# 59. Static Analysis

Use available static-analysis tools.

Preferred tools may include:

```text
clang-tidy
clang-format
compiler warnings
AddressSanitizer
UndefinedBehaviorSanitizer
ThreadSanitizer
```

Do not suppress warnings without understanding the underlying issue.

If a warning must be suppressed, keep the suppression narrow and document why.

---

# 60. Compiler Warnings

Code should compile cleanly with the project's warning configuration.

Do not solve warnings by blindly adding casts, disabling warnings, or suppressing diagnostics.

Fix the underlying issue whenever practical.

---

# 61. AI Agent Behavior

When modifying code, the AI agent MUST:

1. Read the surrounding code before making changes.
2. Identify the existing architecture and conventions.
3. Follow project-specific rules first.
4. Preserve unrelated behavior.
5. Make the smallest reasonable change.
6. Avoid unnecessary refactoring.
7. Prefer standard C++23 facilities.
8. Follow Google C++ style.
9. Apply C++ Core Guidelines principles.
10. Preserve API compatibility unless the task explicitly requests breaking changes.
11. Consider ownership and lifetime.
12. Consider error handling.
13. Consider thread safety when relevant.
14. Consider exception safety.
15. Consider performance only after correctness.

# 63. Decision Rules for the AI Agent

When multiple valid implementations exist, prefer the implementation that:

1. Uses standard C++23 facilities.
2. Makes ownership explicit.
3. Makes lifetime obvious.
4. Prevents invalid states.
5. Has a simple API.
6. Requires fewer dependencies.
7. Is easy to test.
8. Is easy for another developer to understand.
9. Matches existing project conventions.
10. Avoids premature optimization.

Do not choose an implementation merely because it is more "modern."

Modern C++ means **better semantics and clearer intent**, not using every available language feature.

# 64. Examples of Preferred Modern C++

### Ownership

Prefer:

```cpp
auto worker = std::make_unique<Worker>();
```

Avoid:

```cpp
Worker* worker = new Worker();
```

### Optional value

Prefer:

```cpp
std::optional<User> FindUser(UserId id);
```

Avoid:

```cpp
User* FindUser(UserId id);
```

when the pointer is being used as an unclear ownership/result mechanism.

### Error result

Prefer:

```cpp
std::expected<User, UserError> LoadUser(UserId id);
```

when callers need structured error information.

### Non-owning buffer

Prefer:

```cpp
void Process(std::span<const std::byte> buffer);
```

over:

```cpp
void Process(const std::byte* buffer, std::size_t size);
```

### Read-only string

Prefer:

```cpp
void Log(std::string_view message);
```

when the function does not need ownership.

### Duration

Prefer:

```cpp
void Connect(std::chrono::milliseconds timeout);
```

over:

```cpp
void Connect(int timeout_ms);
```

### Range loop

Prefer:

```cpp
for (const auto& user : users) {
  Process(user);
}
```

### Scoped enum

Prefer:

```cpp
enum class State {
  kIdle,
  kRunning,
  kStopped,
};
```

### Override

Prefer:

```cpp
void Run() override;
```

### Locking

Prefer:

```cpp
std::scoped_lock lock(mutex_);
```

over manual locking and unlocking.

# 65. What Not to Do as an AI Agent

The AI agent must NOT:

* Rewrite an entire subsystem for a small bug fix.
* Introduce a framework when the standard library is sufficient.
* Replace working code with abstractions that provide no meaningful benefit.
* Add `shared_ptr` everywhere.
* Add templates merely to make code generic.
* Use `std::move` indiscriminately.
* Use `auto` when hiding an important type harms readability.
* Add comments that simply repeat the code.
* Suppress compiler warnings without investigation.
* Ignore lifetime issues.
* Ignore ownership semantics.
* Assume a raw pointer owns memory.
* Assume a `string_view` or `span` extends an object's lifetime.
* Make unrelated formatting changes.
* Make unrelated architectural changes.
* Change public APIs without considering compatibility.
* Optimize without evidence.
* Prefer clever code over understandable code.
